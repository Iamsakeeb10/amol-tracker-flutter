# Bug: Same-day edit causes streak to jump from 1 to 2

## Root Cause

Two independent streak computations exist that can disagree:

1. **`computeStreakResult()`** (`streak_helper.dart:104`) — used during `submit()`, reads `user.lastLogDate` from Firestore to decide increment/reset. Writes `currentStreak` to Firestore.

2. **`computeStreakFromLogs()`** (`streak_helper.dart:75`) — used by `liveStreakProvider` (`history_provider.dart:278`), fetches actual log documents from Firestore, builds a `Set<String>` of unique `hijriDate` values (excluding backfilled), and counts consecutive days backwards from today.

**The home screen displays `liveStreakProvider`** (`home_screen.dart:238-243`):
```dart
final streakValue = liveStreakAsync is AsyncLoading
    ? null
    : (liveStreak ?? user.currentStreak);
```

### The exact bug path

1. User submits today's amal → `submit()` runs `computeStreakResult()` → if `lastLogDate` is empty (new user or stale), returns `newCurrentStreak: 1` → writes `currentStreak: 1` to Firestore.
2. After submit, `liveStreakProvider` may not recompute immediately because `amalLogRefreshProvider` is **NOT bumped** during `submit()` — it only watches `currentUserProvider` (which is cached and may not re-fetch yet). So the display may briefly show 1 (from the fallback `user.currentStreak`).
3. User edits today's amal → `EditAmalScreen._onSubmit()` calls `invalidateAfterAmalEdit()` which **bumps `amalLogRefreshProvider`** → `liveStreakProvider` **force-recomputes**.
4. `liveStreakProvider` fetches actual logs via `getRecentLogs(uid, limit: 30)`, builds the date set, and calls `computeStreakFromLogs()`.
5. If the user has **any** log from a consecutive Hijri day (yesterday or earlier that's adjacent), `computeStreakFromLogs` counts it → **streak = 2**.

**The jump happens because:**
- `computeStreakResult` relies on `user.lastLogDate` (a single field on the user document) which can be stale/empty.
- `computeStreakFromLogs` reads actual log documents which always reflect reality.
- The edit triggers a refresh of `liveStreakProvider` but `submit()` does NOT bump `amalLogRefreshProvider`, so after submit the stale Firestore `currentStreak` is displayed until the next refresh.

### Additional contributing factor

The `submit()` method (`amal_provider.dart:396-549`) never bumps `amalLogRefreshProvider`. It writes the log and updates streak fields, but the `liveStreakProvider` is only re-triggered by `amalLogRefreshProvider` or `currentUserProvider` changes. Since `currentUserProvider` is cached, there's a window where the display shows the Firestore `currentStreak` value (1) instead of the live-computed value (2).

## Fix Plan

### Option A: Bump `amalLogRefreshProvider` after submit (Recommended — minimal change)

**File:** `lib/providers/amal_provider.dart`

In the `submit()` method, after the log is saved and streak fields are written, bump `amalLogRefreshProvider` so `liveStreakProvider` recomputes immediately:

```dart
// After the streak update try-catch block (~line 507), before the finally block:
_ref.read(amalLogRefreshProvider.notifier).bump();
```

This ensures the home screen immediately recomputes the streak from actual logs after submit, eliminating the window where the stale Firestore `currentStreak` is shown.

### Option B: Use `liveStreakProvider` value in `submit()` result

Instead of writing `currentStreak` to Firestore from `computeStreakResult`, always let `liveStreakProvider` be the source of truth and skip the Firestore `currentStreak` field entirely for display. This is a larger refactor.

### Option C: Sync `lastLogDate` on every log write (including edits)

**File:** `lib/features/history/presentation/screens/edit_amal_screen.dart`

After `editAmalLog()`, also update `lastLogDate` on the user document if the edited log's hijriDate is the latest. This keeps `computeStreakResult` consistent with actual logs for the next submit.

**File:** `lib/core/utils/amal_edit_toggles.dart`

In `invalidateAfterAmalEdit()`, also call `fs.updateUserLastLogDate()` if editing today's log.

## Recommended approach: Option A

It's a one-line change that fixes the root cause (stale display after submit) without touching the edit flow or the streak computation logic.

### Files to modify

| File | Change |
|---|---|
| `lib/providers/amal_provider.dart` | Add `_ref.read(amalLogRefreshProvider.notifier).bump()` after streak update in `submit()` |

### Verification

1. New user submits today's amal → streak should show 1 immediately (no skeleton flash).
2. New user with a log from yesterday submits today → streak should show 2 immediately (not 1 then jump to 2).
3. User submits today, then edits today → streak should remain unchanged.
4. User misses a day, submits next day → freeze modal should appear if freeze is available.
5. Check that the native home screen widget also updates correctly (the `refreshWidgetData` call in the `liveStreakProvider` listener already handles this).
